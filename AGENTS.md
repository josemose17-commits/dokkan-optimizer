# Project rules

## Primary workspace and evidence boundaries

This approved reset authorizes a feature PR. Merge and deployment remain paused until explicitly resumed.

- The primary workspace is kit → intended slot/role → build priorities → available builds → explanation. Browsing/details and named builds are disclosures; the secondary menu contains maintenance/import and sources. Do not restore competing development tabs. Source-example/catalog/legacy URLs intentionally redirect to the workspace; never drop exact state IDs.
- The synthetic team demo and duplicate source comparison screen are retired, including production code/fixtures/tests/styles used only by them. Git history is the archive. Never delete old localStorage automatically, especially `dokkan-team-lab.collection.v1`.
- Reviewed qualitative kit guidance is distinct from mathematical comparison and complete numerical search. Reuse the existing maintenance Ability/Effect/Condition language. Bind kit/policy revisions to exact catalog states; imported/user-entered text does not acquire an admitted policy. Trace reasons to effect IDs. No meta thresholds, universal score, or automatic “stacker = full Additional” rule.
- The admitted Gohan EZA policy is a reviewed early-buildup priority, not an exact winning allocation. Guard timing and persistent Super DEF support the position/rotation inference; native additional and guard-trigger/evasion interactions remain explicit gaps. No arbitrary levels or borrowed Goku formula. An advanced priority override changes advice, not inferred kit design. Slot position and main-rotation/floater assignment are separate.
- The intended product will cover native skills, selectable nodes/stat progression, actual routes/unlocks and equipment together; full allocation is not available for any real character yet. Do not equate the current aggregate 55% profile/equip subset with a complete optimizer.
- Resolve what a state can evaluate before any search (`src/potential/capabilities.ts`: allocation modes, equipment per slot, each objective's status and kit gates) and show it. Never preselect or offer a mode that cannot run; the search scope follows from capabilities and the chosen potential source. Show a single documented progression as a summary, never a one-option selector; every enabled control must have an effect. Keep full-allocation gating and its exact missing-evidence message.
- Allocations come from `src/character-build/allocation.ts`: one option per unlocked choice node of an admitted template, combined with every eligible equipment combination. User-entered current values (skill levels, stat additions) are allowed only when the evaluator declares `customPotential`; label them once “Board requirements not checked.”, keep their technical bounds, and never call them attainable or full allocation. They are an optional field of the saved request; saves without them keep their exact shape.
- States declare kit mechanics (`kit`: absent/present/unknown with evidence). A mechanic that is unknown, or present but not modeled by the evaluator, blocks every objective it could change, with the reason shown before any search.
- Keep data, template mappings, progression/current choices, equipment, context, evaluation, generation, ranking and explanations separate. Templates/mappings pin exact state, profile and data revisions plus evidence. Shared game boards need actual mapping evidence; test graphs and matching aggregate totals are not that evidence. No guessed sliders/node maps.
- Recommendations need objective-specific kit/effect coverage and available baseline/candidate metrics. Missing effects that could change the objective block the result. Unknown metrics never rank as zero. Card ATK/DEF are not damage/survival objectives. Objectives show a model status (Supported, Experimental source-model comparison, Unavailable) instead of an acknowledgement step; experimental results are never presented as confirmed, and their ranking basis is stated. No objective is preselected unless a saved setting supplies it.
- The direct result states what to change, baseline delta, ties and scope. Use exactly “Use my equipment” and “Best available in catalog.” for candidate equipment, kept separate from current equips. No global optimum for truncated searches; the baseline always participates. Preserve equivalent alternatives and objective ties.
- The primary search counts rejected scans, caps evaluations and yields during enumeration AND pairwise dominance checks. Cancellation must invalidate stale results after edits/navigation. Keep synchronous comparison as a small reference API; do not call it for enlarged browser searches. Bound technical input sizes independently of unknown game limits.
- Catalog acquisition is gated independently of optimizer development. Document actual inspected export/sample/license limits once; never implement imagined bulk formats, repeat blocked-provider loops, contact providers or purchase access without authorization. Fixtures do not count as real catalog coverage.
- Keep authored definitions, custom builds, equipment, context and comparison objectives separate. User definitions use `dokkan.character-definitions.v1`; never write the older Goku/collection keys from this editor. Preserve immutable revisions, import previews, relationship/ID checks and storage conflict protection. User-created data is not bundled/source-verified data.
- Keep `src/character-definitions/{domain,validation,evaluation}.ts` pure. Four effect statuses are distinct: recorded, structured, implementation available, supported context. New capability code must fail visibly on unsupported shapes/conditions. Authored flat snapshot arithmetic is a model assumption, not a verified game battle formula. No fallback to Goku or its probability evaluator.
- In character maintenance, custom potential totals/stat additions are allowed with precise input bounds and the visible label “Custom allocation — board compatibility not checked.” They are not proven attainable or free. Do not require a node graph for authoring; board-checked generation stays a separate evidence gate. Do not use “legal build” labels for partial checks.
- Preserve unknown/null values, original wording and explicit evidence assertions. Render imported text safely, bound size/count/nesting and reject future schemas. Compare only common available metrics in one exact snapshot/context; preserve ties and alternative inputs. No universal score or ATK-as-damage objective.
- The first authored evaluator supports one-time flat self-stat snapshot additions and explicit three-valued conditions only. Other families can be recorded without enabling calculation. No probabilities, combat stages or event history are inferred. Extend one family at a time with documented assumptions and independent expected test values.
- Dokkan Info is the preferred provider, but acquisition is paused pending an approved method. Do not scrape, probe endpoints, repeat the same blocked-provider review or treat provider preference as permission. The separate MNprojects published-file factual adapter is admitted; this does not authorize Dokkan Info acquisition. Provider outreach requires explicit user authorization.
- Keep `src/character-data/` independent of React, browser/storage and provider requests. Validate unknown normalized input before admission; a passing schema check is not a source review or permission grant. New adapters must be separate from contracts, search, identity and UI.
- Card forms, EZA/SEZA states and data revisions are distinct identities. Never merge cards by name or infer source-ID conversions. Preserve exact saved Goku IDs and the existing build-catalog revision/storage contract. Report removed or reassigned IDs/aliases before accepting updates.
- The bundled catalog keeps two reviewed Goku states and one reviewed EZA Gohan kit-guidance state, plus the pinned historical MNprojects UR/LR factual projection (792 source identities / 1,106 states). Preserve its AGPL notice/license, author/upstream credit, commit/blob pin and reconciliation manifest. No copied skill prose/artwork, inferred source-ID conversion, arbitrary percentage ladder, embedded-form mapping or optimizer fallback. Source-reported stat columns are optional observations, separate from executable potential profiles and raw stats; ambiguous EZA scopes stay unknown. Updates need a reviewed pin, explicit conflicts/exclusions and saved-ID compatibility checks. Add other individual facts only from actually inspected, permitted public references; pin review/retrieval dates and a source revision/hash where obtainable. If host retrieval is blocked, record that limitation and null revision honestly; do not bypass it or claim a raw response hash. Keep field-level provenance and original short wording. Unknown region/EZA step/links/categories are null, not guessed or documented empty lists. No bulk acquisition from public visibility alone. Test-only fixtures remain isolated.
- Show completeness separately from evidence and executable optimization support. A normalization date is not a retrieval/review date. Independent confirmation needs a dated evidence reference and review; tests and matching websites do not provide it. Raw stats, potential bonuses, flat equips and unknown battle stats remain separate.
- Keep `src/character-build/{domain,legality,generation,evaluation,comparison,registry,explanation}.ts` pure and independent of React, storage, network and data imports. Candidate generation stays separate from evaluation. Never reuse synthetic team ratings or formulas for character performance.
- Select evaluators only through the registry: the catalog state's `optimization.evaluatorId` must name an entry bound to that exact state/card with matching data. Never fall back to another evaluator, character or state. Each entry declares its contexts, objectives, implementation and working-settings key. Test-only registry fixtures stay in test imports and must not reach the production bundle. Explanations must be generated from calculation traces and comparison results, not written separately.
- The admitted real slice is Global English AGL Mystery Super Technique Super Saiyan 3 Goku, fully EZA step 7 / level 140 / SA15, without SEZA, with the filled 55% no-dupe base board. Full node respec remains blocked on exact graph evidence. Do not add guessed nodes or board-validated sliders. This documented profile remains fixed; entered totals in the primary comparison and maintenance are allowed only with their board-compatibility limits. Test-only abstract graphs are not real game data.
- Keep individual real facts in `src/data/real/`, separate from `src/data/fixtures/`. Records need stable internal IDs, honest source aliases, exact state, field-level evidence, support declarations and review/verification dates. A directory or `support: supported` flag does not imply game verification.
- Distinguish source documentation, genuinely independent corroboration/in-game evidence, and passing mathematical tests. Never promote the first or third to independent confirmation. All current real evidence has null independent-verification dates.
- Surface unsupported metrics as unavailable/null, never zero. Offer only supported objectives. Keep card stats, initial-check probabilities and damage separate. No universal weighted score, damage proxy, survival or clear-rate claims.
- Pareto comparisons require identical context and a common explicitly reported set of available metrics. Preserve exact ties. Missing metrics cannot create false dominance. Deduplicate complete exposed evaluations while retaining every alternative legal allocation/equip and its changes/inventory requirements.
- Validate eligibility before ranking, fail closed on unknown restrictions/prerequisites, respect quantities, and distinguish attached current equips from unequipped inventory. Catalog mode means ownership ignored within this catalog only. Never imply respec/equip changes are free or affordable; costs/investment optimization are deferred.
- No current mode is described as verified-only; unresolved silver-orb IDs/restrictions must never enter a mode bearing that label. Disclose the exact catalog/profile/context, source confidence, exclusions, evaluated/unique counts and truncation. A truncated search gives no global optimum. Total legal count is unknown when search stops early.
- Assess access restrictions, copied expressive content, compiled-dataset rights and individual factual recording separately. Missing bulk permission is not automatically a ban on recording individual numbers. Do not assert a legal permission that was not established; no prohibited/internal endpoints, artwork or unlicensed database imports. Maintain `docs/character-build/EVIDENCE.md` and `DATA_ACCESS.md` when evidence changes.
- Keep character storage separately versioned (`dokkan.character-builds.v1`; named saved builds in `dokkan.character-library.v1`). Never overwrite an unreadable or newer stored library without an explicit user replacement; keep stale-revision builds rather than dropping them. Validate schemas/catalog revision and show corruption/blocked-storage warnings. Do not modify the legacy collection key. The primary workspace never autosaves over older working copies; named saves are explicit. Merely editing inputs must not overwrite invalid stored data.
- Test independent hand arithmetic, legal enumeration, restrictions, condition gates, quantities, equivalent variants, Pareto context/ties/missing values and truncation. Hypothetical branch-damage tests are arithmetic tests, not combat verification. Retain relevant engine/storage tests; retire tests solely for removed demo or duplicate-screen behavior.
- Before completion run `npm test`, `npm run typecheck`, `npm run build`, and browser checks at `/dokkan-optimizer/` for kit guidance, the retained comparison, integrated browsing and maintenance (`npm run test:e2e` runs the checked-in Playwright suite). Report actual results. Preserve Node 24, the lockfile and Pages base/workflow. Do not commit generated output, personal builds, dependencies or browser binaries.
- Implement on a feature branch and open a focused PR when requested. The user's standing authorization permits merging eligible implementation PRs after full final-diff self-review; latest required CI and relevant unit/type/build/browser checks pass; no unresolved substantive comments/conflicts remain; saved data is preserved or tested migrations exist; no secrets/private data/unintended generated/unrelated files are included; and docs/capability claims match. Do not bypass protections or force-push main. An explicit task-specific merge/deploy hold still applies.
- For authorized stacked integration, merge dependencies first, retarget/rebase as necessary, reinspect the final diff and run checks on the updated revision. After merging, verify main build/Pages deployment and the live prefix before claiming publication; diagnose regressions without destructive rollback. Ask before purchases/subscriptions, external contact, credential use/sharing, material scope changes, destructive data changes or new hosting/paid infrastructure. Do not ask for routine merge approval when the standing conditions are met.
