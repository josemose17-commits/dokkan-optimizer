# Project rules

## Limited progression-profile/equipment comparison and preserved workbenches

- The limited progression-profile/equipment comparison is the default page (`src/potential/`). Character definitions are secondary maintenance at `?workbench=definitions`; preserve their forms, revisions, comparisons and saves. Preserve the catalog at `?workbench=catalog` (old bare `?state=...` links still open it), source-profile examples at `?workbench=character-build&state=<exact state ID>` and the synthetic team demo at `?workbench=legacy-team`. Do not duplicate or overwrite the exact-state registry/explanation work. See `docs/OPTIMIZER.md` and `docs/CHARACTER_DEFINITIONS.md`.
- The intended product will cover native skills, selectable nodes/stat progression, actual routes/unlocks and equipment together; this is not implemented yet. Do not equate the current aggregate 55% profile/equip subset with a complete optimizer. Default full-potential requests fail closed on missing graph evidence; the selected-profile subset requires explicit scope selection.
- Keep data, template mappings, progression/current choices, equipment, context, evaluation, generation, ranking and explanations separate. Templates/mappings pin exact state, profile and data revisions plus evidence. Shared game boards need actual mapping evidence; test graphs and matching aggregate totals are not that evidence. No guessed sliders/node maps.
- Recommendations need objective-specific kit/effect coverage and available baseline/candidate metrics. Missing effects that could change the objective block the result. Unknown metrics never rank as zero. Card ATK/DEF are not damage/survival objectives. Probability comparisons require explicit acknowledgement of the unresolved source model, not a verification badge.
- The direct result states what to change, baseline delta, ties and scope. Use exactly “Best build using my available equipment” and “Best available in catalog.” No global optimum for truncated searches; the baseline always participates. Preserve equivalent alternatives and objective ties.
- The primary search counts rejected scans, caps evaluations and yields during enumeration AND pairwise dominance checks. Cancellation must invalidate stale results after edits/navigation. Keep synchronous comparison as a small reference API; do not call it for enlarged browser searches. Bound technical input sizes independently of unknown game limits.
- Catalog acquisition is gated independently of optimizer development. Document actual inspected export/sample/license limits once; never implement imagined bulk formats, repeat blocked-provider loops, contact providers or purchase access without authorization. Fixtures do not count as real catalog coverage.
- Keep authored definitions, custom builds, equipment, context and comparison objectives separate. User definitions use `dokkan.character-definitions.v1`; never write the older Goku/collection keys from this editor. Preserve immutable revisions, import previews, relationship/ID checks and storage conflict protection. User-created data is not bundled/source-verified data.
- Keep `src/character-definitions/{domain,validation,evaluation}.ts` pure. Four effect statuses are distinct: recorded, structured, implementation available, supported context. New capability code must fail visibly on unsupported shapes/conditions. Authored flat snapshot arithmetic is a model assumption, not a verified game battle formula. No fallback to Goku or its probability evaluator.
- Custom potential totals/stat additions are allowed with precise input bounds and the visible label “Custom allocation — board compatibility not checked.” They are not proven attainable or free. Do not require a node graph for authoring; board-checked generation stays a separate evidence gate. Do not use “legal build” labels for partial checks.
- Preserve unknown/null values, original wording and explicit evidence assertions. Render imported text safely, bound size/count/nesting and reject future schemas. Compare only common available metrics in one exact snapshot/context; preserve ties and alternative inputs. No universal score or ATK-as-damage objective.
- The first authored evaluator supports one-time flat self-stat snapshot additions and explicit three-valued conditions only. Other families can be recorded without enabling calculation. No probabilities, combat stages or event history are inferred. Extend one family at a time with documented assumptions and independent expected test values.
- Dokkan Info is the preferred provider, but acquisition is paused pending an approved method. Do not scrape, probe endpoints, repeat the same blocked-provider review or treat provider preference as permission. No acquisition adapter is connected. Provider outreach requires explicit user authorization.
- Keep `src/character-data/` independent of React, browser/storage and provider requests. Validate unknown normalized input before admission; a passing schema check is not a source review or permission grant. New adapters must be separate from contracts, search, identity and UI.
- Card forms, EZA/SEZA states and data revisions are distinct identities. Never merge cards by name or infer source-ID conversions. Preserve exact saved Goku IDs and the existing build-catalog revision/storage contract. Report removed or reassigned IDs/aliases before accepting updates.
- Only the existing admitted EZA Goku state is bundled in the catalog. Missing links/categories/leader details are null with reasons, not invented or documented empty lists. Test-only catalog fixtures stay in test imports and are rejected by normal validation. Do not present fixture counts as real coverage.
- Show completeness separately from evidence and executable optimization support. A normalization date is not a retrieval/review date. Independent confirmation needs a dated evidence reference and review; tests and matching websites do not provide it. Raw stats, potential bonuses, flat equips and unknown battle stats remain separate.
- Keep `src/character-build/{domain,legality,generation,evaluation,comparison,registry,explanation}.ts` pure and independent of React, storage, network and data imports. Candidate generation stays separate from evaluation. Never reuse synthetic team ratings or formulas for character performance.
- Select evaluators only through the registry: the catalog state's `optimization.evaluatorId` must name an entry bound to that exact state/card with matching data. Never fall back to another evaluator, character or state. Each entry declares its contexts, objectives, implementation and working-settings key. Test-only registry fixtures stay in test imports and must not reach the production bundle. Explanations must be generated from calculation traces and comparison results, not written separately.
- The admitted real slice is Global English AGL Mystery Super Technique Super Saiyan 3 Goku, fully EZA step 7 / level 140 / SA15, without SEZA, with the filled 55% no-dupe base board. Full node respec remains blocked on exact graph evidence. Do not add guessed nodes or board-validated sliders. This source example remains fixed; custom totals in the separate authoring workbench are allowed. Test-only abstract graphs are not real game data.
- Keep individual real facts in `src/data/real/`, separate from `src/data/fixtures/`. Records need stable internal IDs, honest source aliases, exact state, field-level evidence, support declarations and review/verification dates. A directory or `support: supported` flag does not imply game verification.
- Distinguish source documentation, genuinely independent corroboration/in-game evidence, and passing mathematical tests. Never promote the first or third to independent confirmation. All current real evidence has null independent-verification dates.
- Surface unsupported metrics as unavailable/null, never zero. Offer only supported objectives. Keep card stats, initial-check probabilities and damage separate. No universal weighted score, damage proxy, survival or clear-rate claims.
- Pareto comparisons require identical context and a common explicitly reported set of available metrics. Preserve exact ties. Missing metrics cannot create false dominance. Deduplicate complete exposed evaluations while retaining every alternative legal allocation/equip and its changes/inventory requirements.
- Validate eligibility before ranking, fail closed on unknown restrictions/prerequisites, respect quantities, and distinguish attached current equips from unequipped inventory. Catalog mode means ownership ignored within this catalog only. Never imply respec/equip changes are free or affordable; costs/investment optimization are deferred.
- No current mode is described as verified-only; unresolved silver-orb IDs/restrictions must never enter a mode bearing that label. Disclose the exact catalog/profile/context, source confidence, exclusions, evaluated/unique counts and truncation. A truncated search gives no global optimum. Total legal count is unknown when search stops early.
- Assess access restrictions, copied expressive content, compiled-dataset rights and individual factual recording separately. Missing bulk permission is not automatically a ban on recording individual numbers. Do not assert a legal permission that was not established; no prohibited/internal endpoints, artwork or unlicensed database imports. Maintain `docs/character-build/EVIDENCE.md` and `DATA_ACCESS.md` when evidence changes.
- Keep character storage separately versioned (`dokkan.character-builds.v1`; named saved builds in `dokkan.character-library.v1`). Never overwrite an unreadable or newer stored library without an explicit user replacement; keep stale-revision builds rather than dropping them. Validate schemas/catalog revision and show corruption/blocked-storage warnings. Do not modify the legacy collection key. Reading invalid saved data must not overwrite it before an explicit edit.
- Test independent hand arithmetic, legal enumeration, restrictions, condition gates, quantities, equivalent variants, Pareto context/ties/missing values and truncation. Hypothetical branch-damage tests are arithmetic tests, not combat verification. Keep all legacy tests.
- Before completion run `npm test`, `npm run typecheck`, `npm run build`, and browser checks at `/dokkan-optimizer/` for the primary optimizer and all preserved workbenches (`npm run test:e2e` runs the checked-in Playwright suite). Report actual results. Preserve Node 24, the lockfile and Pages base/workflow. Do not commit generated output, personal builds, dependencies or browser binaries.
- Implement on a feature branch and open a focused PR when requested. The user's standing authorization permits merging eligible implementation PRs after full final-diff self-review; latest required CI and relevant unit/type/build/browser checks pass; no unresolved substantive comments/conflicts remain; saved data is preserved or tested migrations exist; no secrets/private data/unintended generated/unrelated files are included; and docs/capability claims match. Do not bypass protections or force-push main. An explicit task-specific merge/deploy hold still applies.
- For authorized stacked integration, merge dependencies first, retarget/rebase as necessary, reinspect the final diff and run checks on the updated revision. After merging, verify main build/Pages deployment and the live prefix before claiming publication; diagnose regressions without destructive rollback. Ask before purchases/subscriptions, external contact, credential use/sharing, material scope changes, destructive data changes or new hosting/paid infrastructure. Do not ask for routine merge approval when the standing conditions are met.

## Preserved legacy team demo

The following rules apply to the existing synthetic team engine/UI, not to the primary character evaluator.

- Use TypeScript, React, and Vite. Keep `src/engine/` and `src/domain/` independent of React, DOM APIs, storage, network access, and fixture imports. Keep candidate generation separate from evaluation.
- This is a small-collection reference optimizer. Apply eligibility before scoring. Coverage under **both** leaders is required for **every** participant, including both leaders and the friend. Unknown/unsupported eligibility fails closed, including nested rules and mechanic declarations.
- Do not add partial coverage by silently weakening the default. Any future exploration mode must require explicit opt-in, show a warning, retain separate coverage reports, and identify ineligible results.
- Select six distinct owned instance IDs including the selected leader. Represent the friend as a separate seventh participant even when its card ID matches an owned unit. Never deduplicate participants by card ID.
- Target rotations are two disjoint pairs plus three floaters using all seven participants exactly once. The reference search enumerates all 105 unordered layouts. Explain that these are targets, not guaranteed opening rotations.
- Keep coverage, synthetic links, condition fulfillment, and synthetic scenario fit separate. Document all weights and assumptions. A shared-link count is not total strength. Scores are heuristics, never win probabilities or verified damage/survivability.
- Retain deterministic tie-breaking and disclose candidate counts, limits, rejection counts, and truncation. Never claim global optimality for a truncated search. Replacements must pass the same eligibility/evaluation and identify their explored scope.
- Preserve the exact visible notice: “Synthetic demonstration — not real Dokkan recommendations.” Synthetic fixtures belong only in `src/data/fixtures/`; future verified data belongs separately in `src/data/verified/`.
- Never invent real card stats, categories, effects, links, or formulas. No scraping, copying third-party databases/assets, or internal-endpoint probing without verified access and reuse terms. Public visibility and a code license do not establish dataset rights. Update `docs/DATA_SOURCES.md` when evidence changes.
- Records need stable IDs, provenance, reuse terms, review/verification dates, awakening state where applicable, and mechanic support declarations. Null verification dates mean unverified. Unsupported mechanics must remain visible; do not assume their benefit.
- Storage is local, versioned, and validated. Handle blocked storage and corrupt/unknown schemas visibly. The current editor owns at most one instance per synthetic card record; do not add real same-name rules without evidence.
- Engine tests must include small independently enumerated candidate/ranking examples, friend identity, both leader checks, unsupported rules, conditional activation, seven-slot layout partitions, and search truncation. Avoid tests that use the function under test to generate their expected answer.
- Before completion run `npm test`, `npm run typecheck`, and `npm run build`. Report actual results and any checks not performed. Keep the dependency lockfile. Do not commit dependencies, build output, or personal collection data.
- Use a feature branch for implementation. Do not merge or deploy unless requested. Keep changes focused on the approved scope.
